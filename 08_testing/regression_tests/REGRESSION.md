# Regression Strategy — Phase 16

Response to `15_prompts/16_testing_verification/03_regression.prompt.md` (required
8-section format). The executable strategy is
[run_regression.sh](run_regression.sh); this record explains what it enforces and why.

---

## 1. Inputs / assumptions

- TEST-001 requires the regression suite to run automatically on every change; TEST-002
  requires H-gated steps to be visibly skipped, never silently dropped.
- No CI server exists in this workspace. The runner is a single deterministic script
  with one exit code, so any future CI (or a pre-commit hook) wraps it unchanged.
- Safety-critical order drives execution order: build → unit → determinism → fault
  scenarios. A broken build fails fast and reports why.
- SIM-first (DEC-001). Three targets now exist and share one application: `sim`
  (in-process world), `hil` (world on the far side of a framed link, executed in
  this runner) and `stm32` (skeleton, H-gated until the toolchain/board land).

## 2. Work performed

Implemented `run_regression.sh`, which reruns after any change, in order:

1. **Build** — `cmake configure` + `cmake --build -j 4`; compiler errors are surfaced
   in the failure detail (exit status preserved, no filter masks it).
2. **Unit + integration suite** — `fc_tests.exe`; any FAIL line fails the run.
3. **Determinism (SIM-002)** — two independent `fc_sim` processes, same seed, complete
   stdout `diff` must be byte-identical with exit 0 both times.
4. **Ground station (COM-001..004)** — GS self-test (decoder + command-validation
   tests), then an end-to-end decode of two firmware-generated byte logs:
   `nominal` must decode clean (exit 0) and `battery_low` must raise CRITICAL
   state with `--strict` exiting 1. This step is what caught the GS CRC-table and
   shared-sequence-counter defects.
5. **Fault-scenario matrix (SIM-004, SAF/NAV)** — six scenarios run at seed 42 with
   EXPECTED nav sequences asserted by regex (e.g. `imu_dropout` must reach `HOLD.*ABORT`,
   `rc_loss` must reach `LAND.*DONE`), plus `deadline_misses=0` per run. Since Phase 17
   the `ai_loss` scenario is ALSO asserted: nav `TAKEOFF.*HOLD` (flight continues) and
   the perception log degrading to `mode=1` (TOF_ONLY, FC-only ranging carries) —
   the advisory-only contract of DEC-007 enforced in CI.
6. **HIL host rig (Phase 22, DEC-019, HIL-0a..0f)** — the HIL target is built
   (`FC_TARGET=hil` → `fc_hil.exe` + `hil_rig.exe`), then six executed steps:
   - **loopback nominal** — 6000 ticks of the real application over the link:
     asserts `link_stalls=0`, `crc_errors=0`, `seq_gaps=0`, `tx_drops=0`,
     nav `TAKEOFF.*HOLD`, and the per-sensor sample ages (imu ≤1 ms,
     GNSS ≥90 ms, baro ≥18 ms, RC ≤10 ms) — the synchronisation evidence;
   - **DShot capture analysis** — `dshot_analyzer.py` decodes the rig capture
     with an independent CRC-4 implementation: every frame valid, 4 frames per
     tick, 1000 µs period, STOP while disarmed, throttle in range;
   - **fault injection rc_loss / imu_dropout** — the rig applies the fault in
     the shared time base; the step asserts `fault_latency_us ≤ 1000`, that the
     FC's `first_loss_us` equals the rig's applied time, and that the nav
     sequence matches the in-process SIM result;
   - **link robustness** — 18 deliberately corrupted frames must be rejected on
     CRC, counted, resynced, and the mission must still finish (the FC exits 1
     here *because* frames were lost; that is asserted, not tolerated silently);
   - **watchdog interlock** — a negative test: starving the feed must make the
     emulated IWDG expire and the FC exit 3. A pass proves the interlock is
     armed.
7. **Requirement + architecture audit (Phase 23)** — `08_testing/audit_requirements.py`
   parses the baseline (`REQUIREMENTS_DOMAINS.md`, 83 IDs), `VERIFICATION_REPORT.md`
   and this matrix, and fails the run if any baseline ID lacks a status row or a
   traceability row. The same script re-checks FW-001 (no algorithm file includes a
   HAL backend header; 51 files, 0 violations) and FW-004 (no `malloc`/`calloc`/
   `realloc`/`free` in the control path after comment stripping; 0 sites). A
   traceability claim that only holds when someone remembers to run a script decays
   immediately, so this step is what keeps TEST-004/FW-001/FW-004 true on every run.
8. **Manufacturing release package (MFG-001, Phase 25)** — three report lines:
   - **parameter default file regeneration** — `gcc` builds
     `12_manufacturing/tools/dump_param_defaults.c` against the firmware's own
     `parameters.c` + `crc16.c`, calls `params_defaults()` and writes
     `12_manufacturing/parameters/params_defaults.{bin,json}`. The step passes only
     if the regenerated blob still matches the digest the manifest pinned, i.e. the
     "reproducible" in *reproducible manufacturing package* is measured here. The
     generator fails hard if the default path ever touches the flash backend.
   - **release manifest audit** — `audit_release_manifest.py`: digests, stub
     refusal, gate resolvability (a gate pointing at a requirement that is already
     MET fails), BOM revision == package revision, every unpinned BOM row gated,
     gated directories really empty, four **facility-gate probes** (if the blocker
     has quietly disappeared, the run fails and asks for the artifact), FC↔GS
     protocol-version bindings, and the released parameter blob's CRC and 14 fields
     re-derived independently in Python from the layout the C generator reported.
   - **release manifest audit negative tests** — `selftest_audit.py` runs the audit
     as a subprocess against throwaway fixtures and requires all 16 cases to behave
     (control + 14 defect classes + re-baseline round trip). An audit that has never
     failed is a document; this line is what keeps it a check.
9. **H-gated steps (TEST-002)** — STM32 backend build and HIL *hardware*
   execution print `SKIP` with the exact missing prerequisite; they never count
   as passes. The host rig running does **not** satisfy HIL-1..6.
10. **Documentation audit (Phase 26, DEC-024)** — `11_documentation/tools/docs_audit.py`
    runs with the counts this run just measured. It fails on an unmarked placeholder
    or instruction-only stub anywhere in the repository, a banner with content
    appended underneath it, a `DOCUMENTATION_INDEX.md` row whose declared status is
    false in either direction, a broken relative link in an entry document, a derived
    fact that disagrees with the file that owns it (telemetry schema/payload, cmd-gate
    version, parameter blob version/CRC, package revision and item counts), an
    observed count that disagrees with this run (suite size, executed steps, GS tests,
    scenarios, HIL host steps, package audit results), or a number quoted in the
    walkthrough that disagrees with `PROJECT_FACTS.json`. Environment-dependent counts
    are omitted on a reduced host (no gcc/python) instead of failing the run, since
    the facts file describes the documented environment. `--update-facts` is never
    run by the runner: re-baselining is a deliberate act.
11. **V&V review gate (Phase 27, DEC-025)** — `08_testing/vnv_gate.py` classifies
    all 83 baseline requirements from their verification rows (the *last* status
    token wins, so a compound row's caveat counts), requires every evidence
    reference that looks like a path to resolve, and fails if a critical
    loss-of-control requirement is unverified without a written blocker. It also
    fails if `VNV_REVIEW.md` stops quoting the counts it just computed. Its
    negative tests (`--selftest`, 7 fixture trees) run the same CLI as a
    subprocess, per DEC-023.
12. **Release manifest audit (Phase 28, OPS-001)** — `13_release/tools/audit_release.py`
    re-derives the RC-1 manifest from the tree: source tree digest and file count,
    sha256 of all 10 distributed items, genuine absence of the 4 gated artifacts
    (STM32 image, PCB/fabrication data, AI model, per-unit QC records), the build
    targets and reproduction commands, and the rule that OPS-001 must not read
    OPEN while a release exists (a PARTIAL row must name its gap). Its first run
    failed on exactly that rule; the row was corrected at cause. 7 fixture cases
    run the same CLI as a subprocess.
13. **Final A-Z audit (Phase 29)** — `08_testing/final_audit.py` scans every
    project artifact for `TODO`/`FIXME`/`XXX`/`HACK`/`TBD` and requires each
    (file, marker) pair to be registered in `08_testing/FINAL_AUDIT.md` with its
    occurrence count and a disposition (`INTENTIONAL`, `RESIDUAL` with a gate,
    or `FIXED-IN-PHASE-29` with count 0). Both directions fail: an unregistered
    marker, and a register entry whose count no longer matches. 6 fixture cases
    run through the same CLI.

### Step 10 — documentation audit (Phase 26, DEC-024)

The step ran with the counts this run just measured and passed. It was also shown to
fail on purpose during the wiring: with `PROJECT_FACTS.json` still saying 26 executed
steps while the run measured 27, it failed and printed
`--update-facts --observed executed_steps=27`; after that deliberate re-baseline, the
prose-quote check then failed on the walkthrough's stale "26 executed steps" until the
text was updated. Both halves of the single-source-of-truth claim were therefore
exercised in anger, not just asserted: the file must agree with the run, and the prose
must agree with the file.

### Step 11 — V&V review gate (Phase 27, DEC-025)

The gate classified all 83 requirements (49 verified, 34 unverified with written
blockers), resolved 27 evidence references with 0 broken, and confirmed 23/23
critical requirements verified or explicitly blocked; its selftest passed 7/7
fixture cases through the same CLI. The gate also refuses to pass if
`VNV_REVIEW.md` stops quoting those counts, so the review document is coupled to
the classification rather than written beside it.

### Step 12 — release manifest audit (Phase 28, DEC-026)

The RC-1 manifest re-derived clean (tree digest over 588 files, 10/10 items,
4/4 gated artifacts absent), and the audit's first real run had already found the
one contradiction the release could not ship with: OPS-001 still read OPEN. The
row is now PARTIAL with its gap named, and the audit fails the run if it ever
goes back to OPEN while the manifest exists.

### Step 7a — scenario `imu_rc_loss` (Phase 24)

IMU fails at 6 s and RC at 6.2 s, so the most recently latched *cause* is RC loss
while the vehicle can no longer fly. The assertion is on the live flight log, not on
a helper: `nav: TAKEOFF -> HOLD -> ABORT`, `deadline_misses=0`, and
`safety: failsafe=1 action=4` (RC_LOSS reported, MOTOR_STOP taken). A failsafe model
that ranked causes rather than flyability would report `failsafe=1 action=2` (RTL) here
and fail this step.

### Step 5c — ground station telemetry schema v2 (Phase 24)

Feeds an `FC_SIM_GS_LOG` produced by the same scenario into the GS CLI and asserts
four things: the sim exited 0, the GS exited **1** under `--strict`, the output contains
`action=MOTOR_STOP`, and a `SAFETY_ACTION` CRITICAL line is present, with a non-zero
record count. This is the guard on the firmware/GS schema contract: if the two drift,
the v2 frames are refused and the record count goes to zero, which fails the step.

Negative-path check by inspection: the scenario checker fails on wrong sequence, wrong
`deadline_misses`, or nonzero exit; unit step fails on any `FAIL` line or nonzero exit;
build step fails on compiler error. Deliberate-failure injection was not scripted (the
mechanisms are plain `diff`/`grep`/exit-code checks).

## 7. Risks / TBDs

1. No CI trigger exists locally — the runner must be invoked manually or wired into a
   hook; nothing re-runs it automatically yet. Phase 25 raised the stakes slightly: the
   package digest pin means a forgotten re-baseline surfaces only when someone runs the
   suite, so a stale package is invisible until then.
2. Scenario expectations are sequence-regexes on log lines; if the nav log format
   changes, expectations must be updated (documented format dependency).
3. HIL hardware steps (HIL-1..6) remain SKIP placeholders until Phase 08/09 bring-up;
   the host rig (HIL-0a..0f) already runs, so the SKIP must keep naming the board as
   the missing prerequisite rather than the rig design.
4. Runtime is ~2 min (dominated by 6×30 s simulated scenarios in fast mode); acceptable
   now, may need sharding if the suite grows.
5. The documentation audit's prose-quote check only covers number patterns the
   walkthrough actually uses (suite size, executed steps, GS tests, baseline/algorithm
   counts, package audit results). A number phrased some other way is not caught; the
   facts file itself is always re-derived from sources and compared with the run, so the
   values it owns cannot drift silently.
