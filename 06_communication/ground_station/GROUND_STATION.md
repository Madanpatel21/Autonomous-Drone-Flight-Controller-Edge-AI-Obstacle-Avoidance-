# Ground Station — Evidence Record (Phases 20, 23, 24)

Status: COMPLETE (SIM). Host-side tool (Python 3, standard library only). All
evidence comes from decoding byte logs generated by the actual firmware build —
not from hand-built fixtures alone. Serial capture, radio link and real flight
operations are H-gated and NOT executed.

## 1. Inputs / assumptions

- Stream formats from Phase 19 (DEC-015): MAVLink v2 subset, versioned binary
  status record, ICD-02 companion frames.
- COM-001..004, ICD-03. COM-004 is the governing constraint: the GS observes and
  requests; it never arms and never clears an FC/RC gate.
- FC-owned envelopes used for validation mirror `mission_sm.c` defaults
  (16 waypoints, 50 m geofence, 30 m max altitude).
- "Ground station" here = the software that decodes, displays, validates and
  logs. No GUI, no map, no 3-D view is claimed.

## 2. Work performed

- `gs_protocol.py` — decoders for MAVLink v2 (per-message length + CRC_EXTRA
  registry, resynchronizing parse), the versioned status record (magic, schema
  version, sequence, FC-domain timestamp, 53-byte payload **schema v2**, CRC16-CCITT), and
  ICD-02 companion frames (SYNC/CRC, OBSTACLE_SET payload v1 → detections).
  `decode_stream()` walks a mixed capture, resyncs after garbage/corruption and
  counts drops, CRC errors and sequence gaps instead of crashing (COM-002
  degraded-link tolerance).
- `gs_commands.py` — command validation: ARM/DISARM/FORCE_ARM/CLEAR_ARM_GATE/
  OVERRIDE_FAILSAFE rejected unconditionally with a COM-004 reason; mode
  requests limited to HOLD/RTL/LAND; parameter whitelist with FC-owned ranges;
  waypoint validation (cap, geofence radius, altitude envelope).
- `ground_station.py` — CLI: `--from-log [--json] [--strict]`, `--mission`,
  `--set-waypoints`, `--self-test`, `--serial` (prints an explicit SKIP). Health
  classification turns each status record into INFO/WARN/CRITICAL warnings
  (failsafe active, mission abort, battery below RTL/warning bands, altitude
  geofence, companion unhealthy, perception invalid, avoidance STOP/SLOW).
- Firmware side: `FC_SIM_GS_LOG=<file>` makes `fc_sim` emit the production GS
  byte stream (HEARTBEAT + SYS_STATUS + ATTITUDE + status record at 20 Hz) from
  the same encoders the UART path uses.
- Regression runner: new step runs the GS self-test and a real end-to-end decode
  of two firmware-generated logs (nominal must be clean; battery_low must raise
  CRITICAL and exit 1 under `--strict`).

### Phase 24 addition — telemetry schema v2 and the safety action

**Why the schema changed.** The status record carried only the *failsafe name*
(the cause). During an IMU failure with a simultaneous RC loss the vehicle cut
its motors, but a GS reading `RC_LOSS` would have told the operator it was
returning home. The record now also carries the **action the vehicle is actually
taking** (`fc_safety_action_t`: NONE / HOLD / RTL / LAND / MOTOR_STOP), so the
failsafe says *why* and the action says *what the vehicle can still do* (DEC-021).

- Wire format: payload **52 → 53 bytes**, new `uint8_t action` at payload offset 45.
  Version byte bumped to `2`. Both ends changed in the same phase.
- The GS **refuses** an unknown schema version or a wrong payload length rather
  than guessing — a rejected frame is strictly better than a mis-decoded one, and
  `test_status_record_v1_length_is_refused` locks that in.
- Classification: `MOTOR_STOP` raises its own `CRITICAL SAFETY_ACTION` line
  ("vehicle is not flying"); `RTL`/`LAND`/`HOLD` raise `WARN SAFETY_ACTION`.
  `classify()` uses `rec.action`, which is a required field — there is no
  default that could silently read as NONE.
- Unknown action codes decode as `UNKNOWN(n)`, never as NONE.
- `summarize()["last"]` and the human-readable CLI line both include `action`.

**FC-side command gate (Phase 24).** The authority boundary now lives on the FC:
`02_firmware/flight_controller/communication/command/cmd_gate.c` validates every
inbound frame (magic, version, length, CRC16-CCITT) *before* dispatch, refuses
the entire arming class unconditionally (ARM, DISARM_OK, FORCE_ARM,
CLEAR_ARM_GATE, OVERRIDE_FAILSAFE), always accepts EMERGENCY_STOP, whitelists
modes, clamps SET_PARAM to FC-owned envelopes, and bounds waypoint batches.
The GS validation is still useful (fail fast, better operator message) but is no
longer the thing standing between a bad command and the vehicle.

**Still not delivered:** the command transport. The gate exists and is tested;
nothing yet carries a GS frame to it over a real link (COM-004, GS-002, GS-003
remain PARTIAL). `fc_sim` feeds it from `FC_SIM_CMD_LOG`.

### Phase 23 addition

`gs_commands.ALLOWED_COMMANDS` gained **`EMERGENCY_STOP`**: accepted
unconditionally, mapped to the FC's existing bounded LAND action, and still
unable to arm or clear a failsafe. GS-003 requires a GS-originated emergency
path; before this the only safety-relevant command an operator could not issue
from the ground station was, ironically, the emergency one. The command transport
that would carry it to the FC is still unimplemented (COM-004, GS-002, §7).

**Defects found and fixed at cause during this phase:**

1. GS MAVLink CRC was implemented as a 256-entry byte table built from the
   *non-reflected* 0x1021 iteration; it is not bit-identical to the MAVLink
   reference nibble accumulate, so **every real MAVLink frame failed the GS CRC
   check** (0 frames decoded from 240). Replaced with the reference nibble
   implementation, verified against firmware-generated frames.
2. The GS log shared one sequence counter between MAVLink frames and status
   records, making gap detection report 79 phantom gaps in a clean log. The
   firmware now keeps separate counters (DEC-016).
3. `run_regression.sh` resolved the GS directory *after* its own `cd` into
   `02_firmware`, so the new GS step could never find the tool. Path is now
   resolved up front with the firmware path.

## 7. Risks / TBDs

1. No command transport exists yet: validated commands are returned to the
   caller but nothing encodes them onto a link — including `EMERGENCY_STOP`,
   which is therefore validated but not deliverable. Phase 20's remaining work
   is the transport + operator view; the COM-004 rule is enforced in validation,
   not yet against a receiver — the FC must also ignore GS arming regardless
   (SAF-005) when that path is built. This is the single biggest open item for
   GS-002/GS-003 and a named input to the Phase 24 safety analysis.
2. MAVLink coverage is the four-message subset from Phase 19; a real GCS will
   want parameters, RC channels, waypoint upload and mission items. Extending
   the registry is mechanical but must stay in the decoder's authority.
3. Warnings are aggregated across a whole log (first-seen), so a transient
   warning at t≈0 (no companion heartbeat yet) persists in the summary. Honest
   but coarse — a streaming view with dwell times is the natural fix.
4. Battery, attitude and mission fields come from sim-class sensors; no flight
   data has ever been decoded by this tool.

## 8. Next dependency

- **A live command transport** is the single blocking item for GS-002/GS-003 and
  for COM-004. The FC-side `cmd_gate` is written and proven; a UART/MAVLink
  command link (framed, CRC'd, acknowledged) is what would give it a real input
  and the operator a real emergency path.
- Phase 25 (manufacturing) and Phase 26 (documentation) follow; Phase 29 is the
  final audit.
- Warning aggregation is still whole-log first-seen; a streaming view with dwell
  times is the natural next improvement to this tool.
